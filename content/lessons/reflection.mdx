<h2 id="intuition">Attacking the exponent instead of the base</h2>

Week one established that success is `p^n` and that raising `p` has limited returns. **Reflection** changes the equation instead: a critic inspects each step, and a step judged bad is retried. Whether that helps is an empirical question, and the answer depends almost entirely on the critic.

<h2 id="math">Check, Then Retry</h2>

With per-step success `p`, detection rate `d`, and up to `r` retries, a step now succeeds if it is right initially, or if it is wrong, **caught**, and fixed on a retry:

<MathBlock tex="p_{\text{eff}} = p + (1-p)\,d\,\big[p + (1-p)dp + \cdots\big]" />

Everything hinges on `d`. An undetected failure is never retried, so uncaught errors pass through exactly as before. The simulation below runs 20,000 trials per configuration rather than relying on the closed form, so false positives can be included too.

<Callout kind="tip" title="Where the critic is a tool, detection approaches 1">
  The reason reflection works so well in coding agents is that the critic is not a model opinion — it is `pytest`, or the compiler, or the type checker. Those have detection rates near 1.0 and essentially no false positives, which is the regime where the table below shows reflection being transformative. Where the critic is the same model asked *"is this right?"*, `d` is much lower and so is the payoff. **Design tasks so their output is checkable by a tool**, and reflection stops being a hope and becomes a mechanism.
</Callout>

## Summary

Reflection retries steps a critic judges bad, and its value tracks the critic's detection rate almost exactly. A strong critic (`d = 0.9`) lifted an 8-step task from `0.275` to `0.852` for 15% more calls. A weak one (`d = 0.3`, `fp = 0.3`) moved success by `−0.2` and `−0.0` points — nothing — for ~39% more calls. The practical lever is not adding a reflection step but making outputs **tool-checkable**, where detection approaches 1.
