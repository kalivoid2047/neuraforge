<h2 id="intuition">print() works until it doesn't</h2>

`print()` debugging is fine for a five-line script. It stops scaling the moment you need to:
turn it off without deleting it, distinguish "this is expected, informational" from "this is
seriously wrong," or search a production system's history for what happened at 3am. Python's
built-in `logging` module solves all three, and it's what the Neuraforge platform itself uses
throughout its backend.

<Callout kind="tip" title="The five standard severity levels">
  `DEBUG` (detailed diagnostic info) → `INFO` (normal operation milestones) → `WARNING`
  (something unexpected, not yet broken) → `ERROR` (a real failure) → `CRITICAL` (the whole
  program can't continue). Filter by level once, and you can dial between "show me everything"
  and "only alert me to real problems" without touching your code.
</Callout>

<Callout kind="warning" title="One rule that saves real pain later">
  Never log secrets — API keys, passwords, tokens — even at DEBUG level. Logs get written to
  files, shipped to log aggregation services, and read by more people than you expect; treat
  every log line as something that might eventually be seen by someone who shouldn't see a
  credential.
</Callout>

<h2 id="strategy">A systematic strategy for localizing bugs</h2>

When something's broken in code you didn't just write (someone else's, or your own from last
month), guessing where the bug is wastes time. **Bisection** — the same idea as binary search —
finds it faster: pick a point roughly in the middle of the suspect code, check whether the
state is correct there (a log line, a print, a debugger breakpoint), then recurse into whichever
half is actually wrong.

<Callout kind="tip" title="Bisection in one sentence">
  If a 500-line pipeline produces a wrong answer, don't read all 500 lines — check the
  intermediate value at line 250. If it's already wrong there, the bug is in the first half; if
  it's still right, the bug is in the second half. Repeat. This turns an O(n) manual search into
  roughly O(log n) checks.
</Callout>

## Summary

Python's `logging` module replaces ad-hoc `print()` debugging with severity-leveled,
filterable, persistent output — DEBUG for detailed tracing, WARNING for unexpected-but-not-broken
situations, and so on up to CRITICAL. When localizing a bug in unfamiliar code, bisecting the
suspect region (checking intermediate state at the midpoint, then recursing) finds the fault far
faster than reading start to finish.
