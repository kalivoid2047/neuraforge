<h2 id="intuition">Closing week two: a server in about forty lines</h2>

An MCP server that does something useful is small. The subtleties are not in the transport — they are in getting the error semantics right, because a client that confuses the two error channels will misbehave in a way that is hard to diagnose.

<h2 id="math">Two Methods, Two Error Channels</h2>

Two methods carry nearly all the traffic:

- `tools/list` → the tools this server offers, each with an `inputSchema`.
- `tools/call` → invoke one by name with arguments.

And two **distinct** failure channels:

<MathBlock tex="\underbrace{\{\text{result}: \{\text{isError}: \text{true}\}\}}_{\text{the TOOL failed}} \qquad\text{vs}\qquad \underbrace{\{\text{error}: \{\text{code}, \text{message}\}\}}_{\text{the REQUEST was invalid}}" />

<Callout kind="danger" title="Conflating the two error channels causes infinite retries">
  A **tool** error — bad arguments, no results, a failing API — is a `result` with `isError: true`. The agent sees it as an observation and can retry differently, exactly as in week one. A **protocol** error — unknown method, malformed request — is a JSON-RPC `error`, and no rephrasing will ever fix it. A client that treats both as retryable will loop forever against an unimplemented method, burning its budget on a request that cannot succeed. Route them differently.
</Callout>

## Week two summary

Agent memory is three problems: working (the transcript), episodic (past runs), and semantic (Month 10's index) — and only the first is automatically visible, so recall on the others is bounded by retrieval quality. Managing working memory showed that a recency-only summarizer retained **1 of 5** facts against truncation's **2 of 5**: compression is not memory without a retention rule. Episodic memory's most valuable entries are failures. And MCP turns `N×M` integrations into `N+M`, with `tools/list` supplying runtime discovery and two error channels that must not be conflated.
