<h2 id="intuition">Month 9: adapting models instead of building them</h2>

Month 8 built a language model from nothing. That is the right way to *understand* one and the
wrong way to *obtain* one — pretraining a competitive model costs millions of dollars and
trillions of tokens, and almost nobody does it. What almost everybody does is take a model
someone else pretrained and adapt it.

That adaptation is cheap for a specific reason: pretraining already learned the hard, general
part — grammar, facts, reasoning patterns, the structure of language itself. Fine-tuning only
has to teach the model a *task* or a *style*, and that is a far smaller change.

<h2 id="math">Reusing the expensive part</h2>

Month 8's compute model applies unchanged, `C ≈ 6ND`. Fine-tuning keeps `N` and shrinks `D`
enormously:

<MathBlock tex="\frac{C_{\text{finetune}}}{C_{\text{pretrain}}} = \frac{6 N D_{\text{finetune}}}{6 N D_{\text{pretrain}}} = \frac{D_{\text{finetune}}}{D_{\text{pretrain}}}" />

The ratio is purely the ratio of token counts — the model size cancels entirely. A 50M-token
instruction set against 2T pretraining tokens is a factor of 40,000.

<Callout kind="tip" title="Fine-tuning is not a weaker version of pretraining">
  It is a different operation. Pretraining builds general capability from random weights;
  fine-tuning *redirects* existing capability. That is why fine-tuning cannot teach a model
  something it has no substrate for — you can teach a pretrained model to answer in JSON, to
  adopt a persona, or to prefer a domain's vocabulary, but you cannot fine-tune competent
  reasoning into a model that never had it. Knowing which of those you are attempting is the
  first decision in any adaptation project.
</Callout>

<Callout kind="warning" title="The 40,000x ratio hides that fine-tuning still needs the full model in memory">
  Fine-tuning is 40,000× cheaper in *compute*, but Month 8's memory arithmetic has not changed:
  full fine-tuning of a 7B model still needs weights, gradients, and Adam state — the same **112
  GB** that put it beyond a single 80 GB accelerator under DDP. Cheap compute does not imply a
  model that fits.

  This is exactly the gap week two closes. LoRA and quantization attack the *memory* side, which
  is what actually makes single-GPU fine-tuning of a 7B model possible.
</Callout>

## Summary

Fine-tuning reuses pretraining's expensive general learning and only has to redirect it, so its
cost is `D_finetune / D_pretrain` of pretraining — model size cancels, giving a 40,000× reduction
for a 50M-token instruction set against 2T pretraining tokens. That turns 6,076 GPU-days into
219 GPU-minutes. Data requirements fall just as steeply down the ladder from pretraining to
prompting. But compute is not the binding constraint: full fine-tuning of a 7B model still needs
the same 112 GB of optimizer state Month 8 measured. The next lesson looks at the ecosystem that
distributes these pretrained models.
