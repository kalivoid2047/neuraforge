<h2 id="intuition">Closing week two: from a folder of documents to a queryable index</h2>

Everything in week two composes into one pipeline: **load → chunk → embed → store**. It runs offline, and it is the part of a RAG system most likely to be built once and quietly rot.

<h2 id="math">The Ingestion Pipeline</h2>

The stages, and what each one owns:

1. **Load** — parse source files, preserving structure and identity.
2. **Chunk** — split with a chosen size and overlap (10.2.2).
3. **Embed** — vectorize each chunk with a specific model version.
4. **Store** — persist vector, text, and metadata together (10.2.4).

Steps 3 and 4 are coupled in a way that causes real outages: **every vector in the index must come from the same embedding model.** Mixing versions silently corrupts similarity, because the two models place meaning in different coordinates.

<Callout kind="warning" title="Changing the embedding model means reindexing everything">
  There is no incremental path here. Vectors from model A and model B are not comparable, so a partially-migrated index returns nonsense — with no error, just quietly wrong rankings. Record the embedding model version alongside the index, and treat an upgrade as a full rebuild with a cutover. This is the single most common operational mistake in production RAG.
</Callout>

## Week two summary

Ingestion is load → chunk → embed → store, run offline. Chunking decides how specific each vector is, with overlap costing an exactly computable `s/(s-v)` redundancy — `1.88×` at size 20, overlap 10. BM25 supplies lexical matching with frequency saturation, fused with a semantic score because the two fail independently. Metadata handles constraints vectors cannot express, and pre-filtering avoids post-filtering's empty-result failure. And the whole index is tied to one embedding model version: changing it requires a full rebuild, because mixed vectors corrupt similarity silently. Week three queries what we built.
