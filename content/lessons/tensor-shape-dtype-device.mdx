<h2 id="intuition">Every tensor answers three questions</h2>

Before any operation runs, every tensor (in PyTorch, or the NumPy array standing in for it here)
answers three questions: **what shape is it** (how many dimensions, how big is each one),
**what dtype does it hold** (32-bit floats? 64-bit? integers?), and **where does it live** (CPU
memory, or GPU memory)? Getting any of these wrong is one of the most common sources of bugs
when working with real deep learning code — a shape mismatch or a CPU/GPU mismatch produces an
immediate, specific error, which is actually the friendly outcome; the unfriendly outcome is a
silent dtype mismatch that runs but produces subtly wrong results.

<h2 id="math">Shape, dtype, device</h2>

**Shape** is a tuple describing the size along each dimension — `(3,)` is a 1D vector of 3
elements, `(28, 28)` is a 28×28 matrix (e.g. one grayscale image), `(64, 28, 28)` is a batch of
64 such images.

**dtype** controls precision and memory: `float32` is the deep learning default (a good
balance of precision and speed/memory); `float64` is higher precision but rarely needed;
integer dtypes hold labels or indices, not continuous values.

**Device** (CPU vs. GPU) has no equivalent concept in plain NumPy, because NumPy only ever runs
on the CPU. PyTorch tensors carry a `.device` attribute specifically because the *same* tensor
type can live in CPU memory or GPU memory, and an operation between two tensors requires them to
be on the *same* device — moving data with `.to(device)` is an explicit, visible cost, which
matters a great deal once GPUs are actually being used.

```python
# reference only -- torch isn't available in this browser sandbox
import torch

x = torch.zeros((64, 28, 28), dtype=torch.float32)
print(x.shape)    # torch.Size([64, 28, 28])
print(x.dtype)    # torch.float32
print(x.device)   # cpu (until .to("cuda") moves it)

x_gpu = x.to("cuda")   # explicit, visible data transfer -- would error if no GPU is present
```

<Callout kind="tip" title="reshape is (usually) free -- it doesn't copy data">
  `reshape` just reinterprets the same block of memory with a different shape, which is why it's
  effectively instant even for huge arrays — and why mutating a reshaped view mutates the
  original array too, as shown above. This exact behavior is why PyTorch has both `.reshape()`
  and `.view()` (nearly identical, `.view()` requires the data to already be memory-contiguous)
  — the underlying idea is the same one demonstrated here with NumPy.
</Callout>

## Summary

Every tensor (or NumPy array standing in for one) is fully described by its shape, dtype, and
— for PyTorch specifically — device. Shape and dtype have direct NumPy equivalents verified
above; device is PyTorch-specific, tracking whether the data lives in CPU or GPU memory, since
operations require matching devices. Reshaping doesn't copy data, just reinterprets the same
memory — a detail worth knowing because it explains both a performance benefit and a subtle
aliasing gotcha. The next lesson covers broadcasting: the rules for how operations apply to
tensors of different (but compatible) shapes.
