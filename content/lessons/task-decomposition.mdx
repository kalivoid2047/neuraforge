<h2 id="intuition">A plan is a graph, and the graph tells you what can run at once</h2>

A plan written as a list hides its own structure. Written as a **dependency graph** it reveals immediately which steps must wait and which can proceed together — which is the concrete thing planning buys over ReAct.

<h2 id="math">Dependencies, Layers, Cycles</h2>

Each task names its prerequisites. Topological **layers** are the sets of tasks whose dependencies are all satisfied:

<MathBlock tex="L_0 = \{t : \text{deps}(t) = \emptyset\}, \qquad L_{i+1} = \{t : \text{deps}(t) \subseteq L_0 \cup \cdots \cup L_i\}" />

Every task in a layer can run concurrently, so the number of **sequential round trips** is the number of layers, not the number of tasks. The 8-task plan below collapses to 4 layers.

<Callout kind="danger" title="Validate the plan before executing a single step">
  A model asked for a plan will occasionally emit one containing a **cycle** — task A waits on B, B waits on A. Layering detects this immediately, because a round produces no runnable task. An executor that just walks dependencies without checking will block forever instead of erroring, and a hang is far harder to diagnose than an exception. Validate the graph first; the check costs nothing.
</Callout>

## Summary

A plan is a DAG, and its topological layers are the number of sequential round trips required: the 8-task plan above needs only **4**, a `2.0×` reduction that ReAct structurally cannot find. Layering also validates the plan — a cyclic plan produces a layer with no runnable task and errors immediately, rather than hanging an executor that walks dependencies blindly.
