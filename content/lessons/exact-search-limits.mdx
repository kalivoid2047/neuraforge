<h2 id="intuition">Exact search is simple, correct, and eventually impossible</h2>

Brute-force search compares the query against every stored vector. It is trivially correct — it cannot miss a neighbour — and for small corpora it is the right answer. The problem is purely one of scale, and the measurement below shows where the wall is.

<h2 id="math">Linear Cost Per Query</h2>

For `n` documents of dimension `d`, one query costs:

<MathBlock tex="O(nd) \text{ multiply-accumulates, plus } O(n\log k) \text{ to select the top } k" />

Linear in corpus size. Doubling the corpus doubles query latency, forever. There is no constant-factor optimization that changes the exponent.

<Callout kind="tip" title="Exact search is underrated below ~100k documents">
  Read the **last column**, not the milliseconds. Cost per 1,000 vectors stays flat at roughly 33–39 µs across a 200× range of corpus sizes, and that flatness *is* `O(n)` — it is also the part of the result that transfers to your machine, which absolute timings do not. Note the cell measures only up to 200k: a million 128-d float32 vectors is 512 MB, which a browser tab will not allocate. The larger figures are extrapolated from the measured rate and labelled so.
</Callout>

## Summary

Brute-force search is exactly correct and costs `O(nd)` per query — a flat ~33–39 µs per 1,000 vectors from 1k up to 200k, which is that linearity made visible. Extrapolating the measured rate puts a single query over a billion vectors at tens of seconds or worse, and 512 GB of RAM, so the memory wall arrives before the latency wall. Below ~100k documents exact search is genuinely the right default: no index build, no tuning, no recall loss. The next lesson trades exactness for speed.
