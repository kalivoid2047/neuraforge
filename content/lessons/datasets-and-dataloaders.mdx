<h2 id="intuition">Week three: from a toy in-memory array to real training data</h2>

Every training loop this month has used one small array held entirely in memory. Real datasets
— including this month's Image Classifier capstone's dataset — are too large for that, and need
to be split into manageable chunks (**batches**), reshuffled each pass through the data (each
**epoch**), and often loaded from disk on demand rather than all at once. PyTorch splits this
concern into two classes: `Dataset` (defines *what* one example is, and how many there are) and
`DataLoader` (defines *how* examples get batched, shuffled, and served during training) —
matching the general software-engineering idea of separating "what the data is" from "how it's
consumed."

<h2 id="math">Dataset vs. DataLoader</h2>

A `Dataset` needs exactly two things: `__len__` (how many examples exist) and `__getitem__`
(fetch one example by index). A `DataLoader` wraps a `Dataset` and handles batching and
shuffling — the training loop never touches individual examples directly, only whole batches.

```python
# reference only -- torch isn't available in this browser sandbox
from torch.utils.data import Dataset, DataLoader

class MyDataset(Dataset):
    def __init__(self, X, y):
        self.X, self.y = X, y
    def __len__(self):
        return len(self.X)
    def __getitem__(self, idx):
        return self.X[idx], self.y[idx]

loader = DataLoader(MyDataset(X, y), batch_size=32, shuffle=True)
for epoch in range(n_epochs):
    for x_batch, y_batch in loader:   # DataLoader handles batching + reshuffling each epoch
        ...
```

<Callout kind="tip" title="Why shuffle at all, if the data doesn't change?">
  Without shuffling, a network sees examples in the exact same order every epoch. If the
  dataset happens to be sorted or grouped by class (a common real-world situation — data is
  often collected or stored in some non-random order), the network could see all of one class
  in a row, then all of another — nudging its weights toward whatever class it saw most
  recently, rather than learning a stable decision boundary. Reshuffling each epoch (a *new*
  random order every time, not the same shuffle repeated) prevents the network from ever
  learning to depend on a particular ordering.
</Callout>

## Summary

`Dataset` and `DataLoader` separate "what the data is" (length and per-index access) from "how
it's served during training" (batching and shuffling) — implemented from scratch above with a
`SimpleDataset` class and a `simple_dataloader` generator. Reshuffling with a genuinely new
random order each epoch (not the same shuffle reused) prevents a network from learning spurious
patterns tied to data ordering. The next lesson covers a related but distinct concern: how to
split data into train, validation, and test sets, and why that split is what actually reveals
whether a network has learned to generalize.
