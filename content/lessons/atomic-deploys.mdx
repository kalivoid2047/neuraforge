<h2 id="intuition">Deploying is easy; undoing a deploy is the hard part</h2>

Most deploy failures are not detected during the deploy. They are detected minutes later, under load, by users — at which point the only thing that matters is how fast you can get back to the previous version.

<h2 id="math">rename(2) Is Atomic</h2>

Releases are unpacked into timestamped directories and a symlink selects one:

```
/opt/neuraforge/releases/2024-06-01T10-00Z/
/opt/neuraforge/releases/2024-06-02T09-30Z/
/opt/neuraforge/current -> releases/2024-06-02T09-30Z
```

Swapping the symlink is a single `rename(2)`, which the kernel guarantees is **atomic**: every process observes either the old target or the new one, never an intermediate state. Copying files over a live directory has no such property — for the whole duration of the copy the application runs against a mixture of two releases.

<Callout kind="tip" title="Rollback speed is a function of what you kept">
  Rollback is cheap **only** because the previous release is still on disk. Repointing a symlink and restarting takes seconds; rebuilding the previous release requires a working network, a reachable package index, and a build that still succeeds — three things that are not guaranteed, and are least likely to hold during an incident. Keep the last few releases. The capstone's incident is resolved in **2 minutes** for exactly this reason.
</Callout>

## Summary

Releases go into timestamped directories with a symlink selecting the live one, because `rename(2)` is atomic — every process sees the old release or the new one, never a mixture. Copying over a live directory creates a window in which the app runs against two releases at once, producing transient failures that cannot be reproduced later. Rollback is seconds only because the previous release is still on disk; rebuilding it during an incident depends on things least likely to work then.
