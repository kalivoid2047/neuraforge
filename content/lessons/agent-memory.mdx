<h2 id="intuition">Week two: what the agent knows, and where it keeps it</h2>

"Give the agent memory" is three different engineering problems wearing one name. They differ in how long the information lives and — more importantly — in whether it sits in the prompt or has to be fetched.

<h2 id="math">Lifetime and Location</h2>

<table>
<thead><tr><th>kind</th><th>lifetime</th><th>lives in</th><th>built in</th></tr></thead>
<tbody>
<tr><td>working</td><td>one task</td><td>the prompt / transcript</td><td>week 1</td></tr>
<tr><td>episodic</td><td>across tasks</td><td>a log of past runs</td><td>this week</td></tr>
<tr><td>semantic</td><td>indefinite</td><td>a vector index</td><td>Month 10</td></tr>
</tbody>

Only **working** memory is automatically visible. The other two must be *retrieved* — which means recall is a search problem and inherits every failure mode Month 10 catalogued.

<Callout kind="warning" title="Retrieved memory can fail to recall">
  It is tempting to think of episodic and semantic memory as storage that simply works. They are indexes, and Month 10 measured what indexes do to paraphrased queries: `recall@10 = 0.571`. An agent whose memory is a vector store will *silently fail to remember* things it genuinely recorded, roughly as often as that retriever misses. Memory that is retrieved is memory that can be missed, and no amount of storing fixes a recall problem.
</Callout>

## Summary

Working memory is the transcript and is always visible; episodic memory is a log of past runs; semantic memory is a vector index. The distinction that matters is that only the first is in the prompt — the other two are *retrieved*, so recall is a search problem bounded by Month 10's measured `recall@10 = 0.571`. Memory that must be retrieved can be missed even when it was stored correctly.
