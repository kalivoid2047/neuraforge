<h2 id="intuition">Closing week one: why the same math runs 10-100x faster on a GPU</h2>

A CPU is built to do a wide variety of different tasks, one (or a handful) at a time, very
fast. A GPU is built almost the opposite way: thousands of much simpler cores, each slower
individually, but able to do the *same* operation on *many* different pieces of data
**simultaneously**. Deep learning's core operations — matrix multiplication, element-wise
addition, convolution — are exactly this shape: the *same* arithmetic operation, repeated over
enormous numbers of independent values (every weight, every pixel, every example in a batch).
That match between the hardware's strength and the workload's shape is the entire reason GPUs
transformed deep learning from a slow academic curiosity into something trainable in practical
time.

<h2 id="math">Vectorization: the same principle, one level down</h2>

Before even reaching CPU-vs-GPU, the same underlying idea shows up one level down: a
**vectorized** NumPy operation (`a + b` on whole arrays) is dramatically faster than an
explicit Python `for` loop doing the same additions one at a time — because the vectorized
version pushes the entire loop down into pre-compiled C code operating on contiguous memory,
instead of paying Python's per-iteration interpreter overhead. GPU parallelism is this same
"do many identical operations at once, in specialized fast hardware, instead of one at a time in
a slow general-purpose interpreter" idea, taken further.

<Callout kind="tip" title="Why device placement (from two lessons ago) is a real, visible cost">
  Moving a tensor between CPU and GPU memory (`.to("cuda")`) takes real time — it's a physical
  data transfer over a comparatively slow bus. That's precisely why device placement is
  explicit and visible in PyTorch rather than automatic: moving data back and forth carelessly
  (e.g., inside a training loop, every iteration) can easily erase the entire speed advantage the
  GPU was supposed to provide. The rule of thumb: move data to the GPU once, do as much
  computation there as possible, and only move final results back when you actually need them
  (e.g., to print or save).
</Callout>

## Week one summary

This week bridged Month 3's hand-built autograd engine to the real tool professionals use:
PyTorch's `torch.Tensor` generalizes `Value` from scalars to N-dimensional arrays, tracked by
shape/dtype/device; broadcasting lets operations combine differently-shaped tensors without
explicit loops or copies; `.backward()` on tensors computes gradients for entire weight
matrices at once, following the exact same reverse-mode algorithm, verified numerically just
like last month; and GPUs (and vectorization generally) provide the raw speed that makes
training on realistic amounts of data practical. Week two builds actual network layers with
`torch.nn` — the same `Neuron`/`Layer`/`MLP` classes from Month 3, now backed by a real
framework's pre-built, optimized components.
