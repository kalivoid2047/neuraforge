<h2 id="intuition">Week three: actually answering questions</h2>

With an index built, RAG is three steps: embed the question and retrieve, assemble the results into a prompt, and generate. The interesting engineering is almost entirely in step two — what you put in the prompt and what you instruct the model to do with it.

<h2 id="math">Retrieve, Assemble, Generate</h2>

The prompt carries three things: an instruction, the retrieved context, and the question.

```
Answer using ONLY the context. Cite the [id] you used.
If the context does not contain the answer, say so.

CONTEXT:
[1.3.1] What Is a Vector?: ...

QUESTION: ...
ANSWER:
```

Two clauses do most of the work. **"ONLY the context"** discourages the model from answering from parametric memory, which is what produces confident unsourced claims. **"If the context does not contain the answer, say so"** gives the model an exit — without it, a fluent model will invent something rather than return nothing.

<Callout kind="tip" title="Citations are an engineering property, not a prompting trick">
  A model can only cite `[9.1.1]` if that identifier is present in the context it was given, which means the ingestion pipeline must have stored it alongside the chunk text and the prompt builder must have carried it through. Asking for citations from a pipeline that discarded the identifiers produces plausible-looking fabricated ones. Attribution is designed in at ingestion time or it is not available at all.
</Callout>

## Summary

RAG is retrieve, assemble, generate — with the engineering concentrated in assembly. The instruction should restrict the model to the supplied context and explicitly permit abstention, because a fluent model with no licensed exit will invent rather than decline. Citations depend on identifiers surviving from ingestion through to the prompt; a pipeline that discards them will produce fabricated references instead. The next lesson budgets the context.
