<h2 id="intuition">Git for AI projects has one extra wrinkle: big files</h2>

You likely already know git's basics — commit, branch, merge. This lesson isn't a git tutorial
from scratch; it's the handful of habits specific to AI/ML projects, where "just commit
everything" runs into a problem regular software projects rarely face: trained model weights
and datasets can be gigabytes, and git was never designed to store history for files that size
efficiently.

<h2 id="commits">Commit messages that explain "why," not just "what"</h2>

<Callout kind="tip" title="A useful test for any commit message">
  If your commit message just restates the diff ("changed matrix_add function"), it's not adding
  information — anyone can already see that from the diff itself. A good commit message answers
  the question the diff *can't*: why was this change made? What problem, bug, or requirement
  drove it?
</Callout>

Compare:

```
# Low-value: restates the diff
fix bug in matrix_add

# High-value: explains the reasoning the diff alone can't show
matrix_add: validate shapes before adding, not after

Previously a shape mismatch silently zero-padded the shorter row instead
of raising an error, which masked a real bug in the calling code for two
days before someone noticed the output looked wrong.
```

<h2 id="bigfiles">Why trained models and datasets don't belong in git history</h2>

Git stores every version of every committed file, forever, in its history — great for source
code (small, text, changes are meaningful diffs), a poor fit for a 500MB model checkpoint
(binary, doesn't diff meaningfully, and every retrain adds another 500MB to the repository's
permanent history, even if you later delete the file). A repository that accumulates dozens of
old model checkpoints in its history becomes gigabytes just to clone, forever.

<Callout kind="warning" title="The standard fix, briefly">
  Large binary artifacts (datasets, checkpoints) typically live outside git entirely — object
  storage (S3-compatible, or a local path), referenced by a small text file (a path, a URL, a
  hash) that *is* safe to commit. Tools like Git LFS exist to blur this line, but the simplest
  and most portable habit is: **if it's not source code or small config, don't commit it.**
  `.gitignore` is your first line of defense here.
</Callout>

## Summary

Commit messages should explain *why* a change was made — the diff already shows *what* changed.
Large binary artifacts (trained models, datasets) don't belong directly in git history, because
git retains every committed version permanently, even after later deletion — they belong in
external storage referenced by a small, git-safe pointer file instead.
