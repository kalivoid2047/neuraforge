<h2 id="intuition">One place to terminate TLS and enforce limits</h2>

nginx sits between the internet and two loopback-bound applications. Everything it does could technically be done in the app; doing it at the edge means it is done **once**, before a worker process is spent, and cannot be bypassed.

<h2 id="math">What Belongs at the Edge</h2>

The real config's structure:

- two `upstream` blocks with `keepalive`, so connections to the app are reused;
- `location /api/` → the FastAPI service, `location /` → the Next.js service;
- `location /.well-known/acme-challenge/` → the certificate renewal path;
- `proxy_set_header X-Forwarded-*` so the app can see the real client;
- security headers and `client_max_body_size`.

Rate limiting, body size limits, and TLS termination belong here because rejecting a request at the edge costs nothing, while rejecting it in the app has already spent a worker.

<Callout kind="warning" title="This config ships HTTP-only on purpose">
  There is no `443` block, and the file's own comment explains why: `certbot --nginx` rewrites the file in place once a real certificate exists, and a hardcoded HTTPS block pointing at certificates that do not yet exist fails `nginx -t` on **every fresh server**, before certbot can run. The comment also records that certbot does *not* carry the security headers into the block it generates, so they must be re-added. A config honest about its own gaps is worth more than one that looks complete and breaks on first provision.
</Callout>

## Summary

nginx terminates TLS, routes `/api/` and `/` to two loopback services, sets `X-Forwarded-*` so the app sees the real client, and applies security headers and body limits. Controls belong at the edge because rejection there costs nothing while rejection in the app has already spent a worker. And the config ships HTTP-only deliberately — a hardcoded TLS block would fail `nginx -t` on every fresh server before certbot could run.
