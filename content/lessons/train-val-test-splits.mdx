<h2 id="intuition">Training error lies to you about generalization</h2>

A sufficiently flexible model can achieve near-zero error on its training data without having
learned anything generalizable at all — it can simply memorize the training examples,
essentially becoming a lookup table. This is **overfitting**, and training error alone cannot
detect it, because training error measures performance on data the model has already seen and
directly adjusted itself to fit. Detecting overfitting requires evaluating on data the model
*never* trained on.

<h2 id="math">Three splits, three purposes</h2>

- **Train** — the data the model actually learns from (its weights are updated to fit this data)
- **Validation** — held out from training, used to check generalization *during* development —
  comparing architectures, tuning hyperparameters like learning rate, and deciding when to stop
  training
- **Test** — held out from *everything* until the very end, used exactly once to report a final,
  honest performance number — because repeatedly checking (and reacting to) the same held-out
  set during development lets information about it leak into your choices, the same problem
  training error has, just one step removed

<Callout kind="tip" title="Why not just use the validation set as the final number?">
  Every time you look at validation performance and make a decision based on it (try a different
  architecture, adjust a hyperparameter), you're indirectly fitting *to* the validation set —
  not as directly as training does, but the effect is real over many iterations. The test set,
  checked only once at the very end, is what protects against this slower, subtler form of
  overfitting to your own development process.
</Callout>

## Summary

Training error cannot reveal overfitting because it measures fit to data the model directly
adjusted itself against; a validation set (never trained on) reveals the gap between fitting
training data and genuinely generalizing, and a test set (checked only once, at the very end)
protects against overfitting to the development process itself. The polynomial example above
made this concrete: a high-degree fit achieves near-zero training error while performing far
worse than a simpler model on held-out validation data. The next three lessons cover specific
techniques — weight decay, dropout, and batch normalization — that directly combat this
overfitting gap.
