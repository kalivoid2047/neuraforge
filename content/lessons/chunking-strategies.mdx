<h2 id="intuition">Week two: the document preparation that decides retrieval quality</h2>

Indexing whole documents fails in both directions. A long document's vector averages everything it discusses, so it matches nothing precisely; and retrieving it consumes enormous context to deliver one relevant paragraph. **Chunking** splits documents into passages small enough to be specific and large enough to be self-contained — and where you cut matters.

<h2 id="math">Why Split At All</h2>

Three families, in increasing order of respect for the text:

- **Fixed-size** — every `k` tokens. Trivial, uniform, and blind to meaning.
- **Sentence / paragraph** — split on natural boundaries. Variable size, coherent units.
- **Structural** — split on headings, sections, or code blocks. Best when the document has real structure, which curriculum lessons and documentation usually do.

The measurement below uses fixed-size chunking specifically because its failure mode is the easiest to see.

<Callout kind="warning" title="A fixed cut lands wherever it lands">
  The output below prints the actual boundaries of a size-20, overlap-0 split. Every one of them falls mid-sentence — `...for k segments this is |CUT| minimized when k equals...`. Neither chunk contains the complete statement, so a query needing it matches each only partly. This is not a contrived example; it is what fixed-size chunking does by construction.
</Callout>

## Summary

Chunking splits documents so their vectors are specific rather than averaged, and so retrieval spends context efficiently. Fixed-size splitting is simple and blind: the printed boundaries show every cut landing mid-sentence, leaving neither chunk with the complete statement. Sentence and structural chunking respect the text's own units at the cost of uniform size. The next lesson measures what overlap buys and what it costs.
